# Changelog

All notable changes to the viva skills are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Each section is the date the change merged (YYYY-MM-DD, Europe/London). Skill versions are in each `SKILL.md` (`metadata.version`).

## 2026-11-26

### Added

- Two more scenario evals. `dispute-after-log` checks a dispute that stands after the line is written: the fixture's commit message says "at most 5 attempts" while the code has `MAX_ATTEMPTS = 3`, and a scripted dispute names the mismatch. The original line must be unchanged and one correction line with the same key and grade `disputed` must follow. `practice` runs `/viva practice 1` against a fixture repo with a merge commit and a stub `gh` on PATH (`pr list --json`, `pr diff`), and checks for one `practice` log line and one experiment-file line with a think/recall value that agrees with it. `scripts/check-eval.py` gained the `correction` and `experiment_fields` checks, the runner takes a per-scenario `fixture-repo.sh` and `bin/`, and `scripts/test-check-eval.sh` covers each new check, the fixtures and the stub offline. Why: the first evals left these two behaviours from the original ticket unchecked ([adamsuk/software-factory#502](https://github.com/adamsuk/software-factory/issues/502)).
- A manual **Evals** workflow (`.github/workflows/evals.yml`) runs `scripts/run-evals.sh` on `workflow_dispatch`. It skips itself unless the `ANTHROPIC_API_KEY` secret is set, never runs on a fork, and has a per-call budget and a run-wide cost cap as inputs. Why: the evals existed but nothing ran them ([adamsuk/software-factory#502](https://github.com/adamsuk/software-factory/issues/502)).

### Changed

- `scripts/run-evals.sh` has a run-wide cost cap, `EVAL_MAX_TOTAL_USD` (default 5): no call starts once it is spent, and each call's budget is cut to what is left. Why: a per-call budget alone doesn't bound a whole run ([adamsuk/software-factory#502](https://github.com/adamsuk/software-factory/issues/502)).

## 2026-11-25

### Added

- `scripts/check-skill-invariants.sh` checks rules each SKILL.md must keep beyond frontmatter and versions:
  - corrections copy every field;
  - the format and example agree;
  - the never-rewrite and privacy lines stay;
  - step 7 excludes someone else's change and practice runs, and never posts;
  - PR-description triggers say "own words";
  - practice never diffs against merge-base;
  - every logged scope is offered;
  - viva-assess applies corrections and keeps practice out of drift.

  Given the platform's `log-schemas.json`, it also checks that every scope and value the skill writes is one the platform documents. `scripts/test-check-skill-invariants.sh` breaks each rule on a copy of the skills and checks the right failure is reported. Both run in CI and the factory test command, and the live-schema check runs alongside the contract check. Why: every one of these rules was broken this week and caught only by review; now CI catches it ([adamsuk/software-factory#501](https://github.com/adamsuk/software-factory/issues/501), [#25](https://github.com/adamsuk/viva-skills/pull/25)).
- Scenario evals in `evals/` run the skills in a real agent (`claude -p`, multi-turn) against a fixture repo, with a throwaway HOME. `scripts/check-eval.py` checks what they wrote against the skill's own format line: field count, skill version, full timestamp, grade, and per-scenario fields. There are three scenarios: last commit, "no log" and a wrong CodeRabbit claim. `bash scripts/run-evals.sh` runs them on demand; they cost real usage and aren't run in CI. `scripts/test-check-eval.sh` tests the checker offline. Why: CI checks the instructions, not what an agent does with them. A first run found a real defect, fixed below ([adamsuk/software-factory#501](https://github.com/adamsuk/software-factory/issues/501), [#28](https://github.com/adamsuk/viva-skills/pull/28)).

### Changed

- `viva` 0.6.3 always writes the full `YYYY-MM-DD HH:MM` timestamp, from `date` or by asking, even when it prints the line instead of writing it. Why: in a scenario eval the agent couldn't read the clock and printed a line with the time left out, which the log format doesn't allow ([adamsuk/software-factory#501](https://github.com/adamsuk/software-factory/issues/501), [#28](https://github.com/adamsuk/viva-skills/pull/28)).
- `viva` 0.6.2 has a practice mode. `/viva practice [N]` (default 5) works through your own past merged PRs, newest first, skipping any already checked. Each PR gets the usual single question, logged with scope `practice`. After each reveal it asks whether you had to think or just recalled, and appends that to a separate local file, `~/.agents/viva-experiment.md`. Practice targets each PR's own change (`gh pr diff`), skips PRs already checked under `pr-N` or their branch name, and appends a corrected line to the experiment file when a dispute stands. `viva-assess` 0.4.1 summarises the file on request: think, recall and mixed counts, grades within each (disputed checks left out, the last line per PR wins), and progress toward 20. It leaves practice checks out of drift. This is also release 0.6.2. The log line format is unchanged. Why: Viva's experiment 1 (20 of your own merged PRs; how often did you have to think rather than recall?) meant invoking `/viva` 20 times by hand with nowhere to keep the rating, and `evaluate-it` is the open ground ([adamsuk/software-factory#497](https://github.com/adamsuk/software-factory/issues/497), [#24](https://github.com/adamsuk/viva-skills/pull/24)).
- `viva` 0.6.1 has an optional last step before you post. It offers to help write the PR description in your own words: it asks why, what, and the decision you're least sure of, and fixes only spelling and layout. It also suggests an `Assisted-by` trailer naming the tool that helped, based on how the change was made, and asks first when that isn't recorded. You can also start it by saying "help me write my PR description in my own words". Nothing is committed or posted unless you ask, and nothing from this step is logged. This is also release 0.6.1: `VERSION`, and the README's tag and pin examples, move to 0.6.1. Why: the guide's Best-practice recommendations `own-description` (the description is where a reviewer sees whether the author understands the change) and `disclose` (it tells the reviewer where to look harder) had no support in the skills ([adamsuk/software-factory#495](https://github.com/adamsuk/software-factory/issues/495), [#23](https://github.com/adamsuk/viva-skills/pull/23)).

## 2026-11-24

### Changed

- `viva` 0.6.0 writes log schema 0.6.0, the 0.5 line plus `bot`: for a review-comment check, the bot that made the comment, by its short lowercase name (`coderabbit`, `copilot`), or `unknown`. Every other scope writes `n/a`. `viva-assess` 0.4.0 gives the bot-comment counts per bot, and its drift check compares hand-offs only across checks that record `ai-use` (at least 3 on each side), the same as the map. Corrections are written in the current format, and fields an older line lacks take their defaults. This is also release 0.6.0: `VERSION`, and the README's tag and pin examples, move to 0.6.0. These are minor bumps because the log format changed. Needs adamsuk/viva#20 live. Why: the guide's `track-acceptance` recommends tracking each bot and re-testing it when its model changes, and counts pooled across bots can't do that ([adamsuk/software-factory#494](https://github.com/adamsuk/software-factory/issues/494), [#22](https://github.com/adamsuk/viva-skills/pull/22)).
- Release 0.5.1: `VERSION` is now 0.5.1, matching `viva` 0.5.1 (`viva-assess` 0.3.1), and the README's tag and pin examples use `v0.5.1`. Why: correction lines (#20) merged since 0.5.0 ([#21](https://github.com/adamsuk/viva-skills/pull/21)).
- `viva` 0.5.1 corrects instead of rewriting. If a dispute stands, or a bot comment's verdict changes, after the line was logged, the skill appends the same check again (same timestamp, repo, branch or PR, commit and topic) copying every other field, with the new grade or `bot-claim`. The personal map and `viva-assess` 0.3.1 keep the last line for each check. Needs adamsuk/viva#19 live. Why: the skill never rewrites a line, so a dispute that stood after logging left the faulty question counted as a miss ([adamsuk/software-factory#493](https://github.com/adamsuk/software-factory/issues/493), [#20](https://github.com/adamsuk/viva-skills/pull/20)).
- Release 0.5.0: `VERSION` is now 0.5.0, matching `viva` 0.5.0 (`viva-assess` 0.3.0), and the README's tag and pin examples use `v0.5.0`. Why: `viva` writes log schema 0.5.0 (with `bot-claim`) since #18 ([#19](https://github.com/adamsuk/viva-skills/pull/19)).
- `viva` 0.5.0 writes log schema 0.5.0, the 0.4 line plus `bot-claim`. For a review-comment check, it records whether the bot's claim held (`held`, `partly`, `wrong`); every other scope writes `n/a`. The first-run notice mentions it. `viva-assess` 0.3.0 reads it and reports in one line how many checked bot comments held. These are minor bumps because the log format changed. Needs adamsuk/viva#15 live, which adds the schema. Why: the guide's `track-acceptance` recommends tracking how often bot comments hold up, because a bot nobody listens to trains people to ignore it. The skill verified each claim but never kept the verdict ([adamsuk/software-factory#491](https://github.com/adamsuk/software-factory/issues/491), [#18](https://github.com/adamsuk/viva-skills/pull/18)).
- Release 0.4.4: `VERSION` is now 0.4.4, matching `viva` 0.4.4 (`viva-assess` 0.2.2). The README lists the review scope, re-checks, and confidence and drift, and its tag and pin examples use `v0.4.4`. Why: three skill features merged since 0.4.2, which was never tagged ([#17](https://github.com/adamsuk/viva-skills/pull/17)).
- `viva` 0.4.4 has a review scope: before approving a PR someone else or an agent wrote, the reviewer gets one question on its key behaviour. The reveal says this is practice, not a gate, and suggests asking the author or agent about anything they couldn't explain. It is logged with scope `review`, and `ai-use` records how the PR was made (`agent` for an agent-built PR, otherwise `unknown`). Why: the guide's `quiz-reviewers` recommends asking reviewers too, because approval is a claim of understanding, and in agent-heavy repos the reviewer is often the only human who reads the change ([adamsuk/software-factory#489](https://github.com/adamsuk/software-factory/issues/489), [#16](https://github.com/adamsuk/viva-skills/pull/16)).
- `viva-assess` 0.2.2 reports whether confidence separates knowing from guessing: the understood count per confidence band, and one sentence when high and low each have 3 or more checks. With 10 or more checks it also compares the latest 5 with the earlier ones, and names at most one change in the wrong direction (understood rate down, or delegated/agent share up, by 20 points or more) as a nudge. Why: EXPERIMENTS.md asks whether confidence improves the signal, and `watch-habituation` warns that scrutiny thins while approval stays high. The report only flagged single confident-wrong checks ([adamsuk/software-factory#487](https://github.com/adamsuk/software-factory/issues/487), [#15](https://github.com/adamsuk/viva-skills/pull/15)).
- `viva` 0.4.3 re-checks a thin area. When the log shows a topic whose latest check was missed or partial a week or more ago, and the change in scope touches that area, the question is a re-check on it, announced in one line and logged under the same topic. Changes that don't touch such an area get a fresh question, as before. Why: spaced retrieval of what you got wrong is the practice the research rates Strong, and the personal map already flags these topics, but nothing acted on the flag ([adamsuk/software-factory#486](https://github.com/adamsuk/software-factory/issues/486), [#14](https://github.com/adamsuk/viva-skills/pull/14)).
- Release 0.4.2: `VERSION` is now 0.4.2, matching `viva` 0.4.2 (`viva-assess` 0.2.1), and the README's tag and pin examples use `v0.4.2`. Why: the topic-reuse change and the installer fixes merged since 0.4.1, and no release tag existed yet ([#13](https://github.com/adamsuk/viva-skills/pull/13)).
- `scripts/install-hook.sh`: the check that refuses a shared `core.hooksPath` now walks the path the way `mkdir -p` does, resolving each existing component before the next `..`, so a path like `<repo>/new/../link/../hooks` (with `link` a symlink out of the repo) is refused instead of creating `hooks` beside the link's target, and a newline in the path no longer hides what follows it from the check. Why: CodeRabbit found it just after #10 merged ([adamsuk/software-factory#485](https://github.com/adamsuk/software-factory/issues/485), [#12](https://github.com/adamsuk/viva-skills/pull/12)).
- `AGENTS.md`: a skill's minor version now moves only when its log line's format changes (its fields, a new platform schema); behaviour, wording and changes to the values written into existing fields are patch bumps. Why: the platform matches log lines by `major.minor`, so a minor bump for behaviour alone (as the old rule asked) would fail the contract check and make the personal map read the lines with the wrong schema ([adamsuk/software-factory#478](https://github.com/adamsuk/software-factory/issues/478), [#11](https://github.com/adamsuk/viva-skills/pull/11)).
- `viva` 0.4.2 picks the topic before logging: it reads the topic names already in your local log and reuses one exactly when this check is about the same area, otherwise writes a new 2 to 4 word topic naming the area. It reads only the topic field and never shows other lines. `viva-assess` 0.2.1 treats clearly identical areas under different wordings as one topic and says which it merged. Why: topics are free text, so one area split across wordings and weakened the thin-area and re-check signals on the personal map ([adamsuk/software-factory#478](https://github.com/adamsuk/software-factory/issues/478), [#11](https://github.com/adamsuk/viva-skills/pull/11)).

## 2026-11-23

### Added

- An opt-in reminder after commits: `scripts/install-hook.sh` installs `hooks/post-commit` in the repository you run it from. After every third commit (`VIVA_REMIND_EVERY` to change) it prints one line suggesting `/viva`; `VIVA_REMIND=off` silences it. It never blocks a commit, never logs and never uses the network; it won't replace another post-commit hook (or install into a shared `core.hooksPath`) without `--force`, never writes through a symlinked hook, shrugs off a damaged counter, and `--uninstall` removes only its own hook. Tested in `scripts/test-hook.sh`. Why: the personal map only helps if checks happen, and every check depended on remembering to type `/viva`; the MVP deferred an auto-trigger, and the research favours one small question as a minute's practice, never a gate ([adamsuk/software-factory#477](https://github.com/adamsuk/software-factory/issues/477), [#10](https://github.com/adamsuk/viva-skills/pull/10)).
- A contract check between the skills and the Viva platform: `scripts/check-log-contract.sh` finds every example log line in each `SKILL.md` and checks that a schema in the platform's `log-schemas.json` covers its version (exact, or `major.minor.x`) and that the line has that schema's number of fields. CI runs it against the live file; `scripts/test-check-log-contract.sh` tests it against a fixture. Why: the worst bug in the 2026-11-23 audit was the skill writing `0.3.3` lines that no platform schema matched, and nothing caught it ([adamsuk/software-factory#475](https://github.com/adamsuk/software-factory/issues/475), [#8](https://github.com/adamsuk/viva-skills/pull/8)).
- Factory onboarding: `scripts/validate-skills.sh` checks every `SKILL.md` (frontmatter, `name` matches the folder, `metadata.version` is X.Y.Z, and every "currently X.Y.Z" and example log line in the body matches it), with tests in `scripts/test-validate-skills.sh`. A `test` workflow pinned by SHA runs both on every pull request, plus the changelog check, a size-label caller, `.github/factory.yml`, `AGENTS.md`, `CODEOWNERS`, and issue and pull-request templates. Why: nothing checked the skills, so a version mismatch between a skill and the log it writes could ship unnoticed, and the factory had no test command to gate changes here ([adamsuk/software-factory#456](https://github.com/adamsuk/software-factory/issues/456), [#1](https://github.com/adamsuk/viva-skills/pull/1)).
- State as of onboarding: `viva` 0.3.3, `viva-assess` 0.1.5.

### Changed

- `scripts/check-log-contract.sh`: a schemas file that exists but can't be read now exits 2 with a message instead of crashing with exit 1, and an example line ending in ` | ` (an extra empty field) is now counted and rejected; the line used to be trimmed before splitting, which dropped that field. Why: CodeRabbit found both just after #8 merged ([adamsuk/software-factory#483](https://github.com/adamsuk/software-factory/issues/483), [#9](https://github.com/adamsuk/viva-skills/pull/9)).
- The README lists what each skill now does (dispute a question, check a bot review comment, record how the change was made) and how releases work: `VERSION` is the repository release (now 0.4.1, matching `viva`), each release is tagged `v<VERSION>`, and the pin example uses a tag that will exist. `scripts/validate-skills.sh` also checks `VERSION` is X.Y.Z. Why: the README described only the 0.3-era skill, told users to pin `v0.1.0` though the repo had no tags, and `VERSION` said 0.1.0 while the skills were at 0.4.1 and 0.2.0 ([adamsuk/software-factory#473](https://github.com/adamsuk/software-factory/issues/473), [#7](https://github.com/adamsuk/viva-skills/pull/7)).
- `viva` 0.4.1 has a review-comment scope: point it at a bot's review comment you plan to forward or act on, and it verifies the comment's claim against the code first, then asks one question that tests whether you could defend or refute it. The reveal says whether the bot was right. Logged with scope `review-comment`. Why: the guide recommends that whoever forwards an AI comment owns it and gets the same small question as authors. Prior art found no tool that does this, and developers rejected more of one review bot's comments (56%) than they accepted (36%) ([adamsuk/software-factory#466](https://github.com/adamsuk/software-factory/issues/466), [#6](https://github.com/adamsuk/viva-skills/pull/6)). Source: [Is Agentic Code Review Helpful?](https://arxiv.org/abs/2607.03316) (3 July 2026).
- `viva` 0.4.0 records how the change was made (`ai-use`: `hand`, `explained`, `generated-then-understood`, `delegated`, `agent`, `unknown`) and writes log schema 0.4.0, the 0.3 line plus that field. It infers the value when the session makes it clear, otherwise asks one multiple-choice line with the confidence prompt, and never guesses `hand`. A partial or missed answer on a delegated change gets one sentence pointing to asking why. `viva-assess` 0.2.0 compares grades by `ai-use` and still reads 0.3 lines. Why: in a randomized trial, how people used AI predicted their understanding (delegation 24% to 39%, asking why or generate-then-understand 65% to 86%), and the log recorded nothing about it. Needs adamsuk/viva#7 live, which adds the schema ([adamsuk/software-factory#465](https://github.com/adamsuk/software-factory/issues/465), [#5](https://github.com/adamsuk/viva-skills/pull/5)). Source: [How AI assistance impacts the formation of coding skills](https://www.anthropic.com/research/AI-assistance-coding-skills) (29 January 2026).
- `viva` 0.3.5 lets you dispute a question. The reveal ends with one line offering it; on a dispute the agent re-checks the premise and the expected answer against the code, says whether the dispute stands, and if so logs the grade `disputed` instead. `viva-assess` 0.1.7 leaves disputed checks out of thin and confident-wrong and reports them as a question-quality note. Why: model-written questions about code are not reliably correct (AutoMCQ, Moderate), and the guide recommends letting people dispute a question so a bad one is fixed before it counts. The personal map reads `disputed` the same way (adamsuk/viva#5) ([adamsuk/software-factory#461](https://github.com/adamsuk/software-factory/issues/461), [#4](https://github.com/adamsuk/viva-skills/pull/4)). Source: [AutoMCQ](https://arxiv.org/abs/2505.16430).
- `viva` 0.3.4 says what it keeps before the first question on a device: the fields of the log line, that it stays in `~/.agents/viva-log.md` and is never sent anywhere, why, how long, and that "no log" skips it. Both skills now say the personal map keeps a pasted log "in that browser on that device" instead of naming IndexedDB (`viva-assess` 0.1.6). Why: the guide's Best practice is to say what is collected, why, and for how long before the first question, and the map keeps the log in local storage ([adamsuk/software-factory#460](https://github.com/adamsuk/software-factory/issues/460), [#3](https://github.com/adamsuk/viva-skills/pull/3)).
- The README says what the skills actually do with your answers: one line per check in `~/.agents/viva-log.md` on your device, never posted or shared unless you ask, and a new What is stored section lists the fields, where they live, why, and how to delete them. It said the default was a private GitHub gist, which contradicted both skills. Why: the research is Strong that monitoring without a clear, transparent purpose goes with worse attitudes, and the guide recommends saying what is collected before collecting it ([adamsuk/software-factory#457](https://github.com/adamsuk/software-factory/issues/457), [#2](https://github.com/adamsuk/viva-skills/pull/2)).
